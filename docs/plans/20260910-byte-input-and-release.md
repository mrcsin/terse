# Byte input, package naming and GitHub Packages

## Overview

Three threads land in one release, `v1.1.0`: byte-based input, the lowercase package id, and a
second publish target.

`terse` reads source as text today, and each of the two input paths distorts it differently.
`Terse/Program.cs:49` uses `File.ReadAllText`, which silently drops a UTF-8 byte order mark;
`Terse/Program.cs:13` uses `Console.In.ReadToEnd()`, which decodes with the console code page and
therefore names the wrong code point in every `non-ascii` message. The same bytes get two different
verdicts depending on how they reach the tool, and the git hook in `examples/pre-commit` runs on the
path that lies.

This plan routes both paths through one byte entry point, decodes once with UTF-8, and skips a
leading byte order mark before the ASCII scan and before parsing. Encoding stays owned by
`.editorconfig` (`charset`) and `dotnet format --verify-no-changes`, the way line endings, final
newline and indentation already are; `terse` gains no encoding policy and no new rule.

The package id becomes `terse` in place of the assembly-derived `Terse`. nuget.org has recorded id
casing per version since April 2021 and displays the casing of the latest version, so publishing
`1.1.0` under the new id renames the listing; the fix landed in NuGetGallery#3349, whose closing note
says a package owner resolves casing by pushing a new latest version.

The release workflow gains a second push, to the GitHub Packages NuGet registry. That registration
does not exist yet, so its casing is set by the first push, and the package page appears at
`github.com/mrcsin/terse/pkgs/nuget/terse` with the packed `README.md` as its body. GitHub Packages
requires authentication even for public packages, so this target is a mirror and a package page, not
an install source; nuget.org stays the way consumers install the tool.

dotnet run --project Terse -- --stdin bom.cs < bom.cs # prints non-ascii U+FEFF, exits 1

## Solution Overview

One entry point takes bytes and owns the decode:

```
File.ReadAllBytes / Console.OpenStandardInput
        |
        v
Rules.Check(ReadOnlySpan<byte>)
        |  skip EF BB BF when present
        |  decode UTF-8, strict
        v
CheckText(string)  ->  Roslyn  ->  the seven existing rules
```

The byte order mark is skipped, not reported. `terse` already ignores every other core
`.editorconfig` property (`end_of_line`, `insert_final_newline`, `indent_style`,
`trim_trailing_whitespace`), and `charset` is the fourth member of that set. It belongs to
`dotnet format`, which fails with `error CHARSET` when a file disagrees with `.editorconfig`.
Reporting the mark would turn `terse` into an encoding linter and would fight the BOM that
`dotnet new` still writes.

Invalid UTF-8 currently decodes to `U+FFFD`, which makes `non-ascii` name a character that is not in
the file. Strict decoding turns that into one honest violation at the first bad byte, and it also
covers a UTF-16 file, because `FF FE` is not valid UTF-8.

## Technical Details

- `Rules.Check(ReadOnlySpan<byte> source)` becomes the only public check entry, and
  `Rules.Check(string)` at `Terse/Rules.cs:28` becomes
  `private static List<Violation> CheckText(string source)`.
- BOM skip: `if (source.StartsWith(Encoding.UTF8.Preamble)) source = source[3..];`. Do not write
  `"\xEF\xBB\xBF"u8`: that literal is the UTF-8 encoding of three characters U+00EF U+00BB
  U+00BF and yields six bytes, `C3AFC2BBC2BF`, so it never matches. `"\uFEFF"u8` is the other
  correct form.
- `Encoding.UTF8.GetString` does not remove a preamble on its own, so the slice is explicit.
  `StreamReader` removes a preamble regardless of `detectEncodingFromByteOrderMarks` when its
  encoding is `Encoding.UTF8`, and keeps it when the encoding is `new UTF8Encoding(false, true)`,
  whose `Preamble` is empty; neither behaviour is worth depending on.
- Decode: `new UTF8Encoding(false, throwOnInvalidBytes: true).GetString(source)`. A
  `DecoderFallbackException` yields one violation and the file is not parsed. The message is
  `invalid UTF-8 byte 0x{BytesUnknown[0]:X2}; source is ASCII only`, under the existing `non-ascii`
  rule name.
- Line number for the invalid-byte violation comes from counting `\n` bytes before the failing
  offset. `DecoderFallbackException.Index` is the absolute offset for a single `GetString` call over
  the whole buffer (measured 2026-09-10 on .NET 10: a `0xFF` at offset 13 reports `Index=13` for
  both the `byte[]` and the `ReadOnlySpan<byte>` overload).
- Stdin: `Console.OpenStandardInput()` copied into a `MemoryStream`, then `ToArray()`. Do not set
  `Console.InputEncoding`: the setter calls `SetConsoleCP` and leaves the user's console at code page
  65001 after the process exits.
- `Lint` at `Terse/Program.cs:68` takes `ReadOnlySpan<byte>` instead of `string`. That is legal
  because `Lint` is a synchronous local function with no iterator or async body.
- Rule names and the report format do not change, and the seven rules stay as they are. The only
  new message is the invalid-byte one above, under `non-ascii`. The package version goes to 1.1.0
  because the public check signature changes.
